# 8051 — modelo educacional

## ⚠️ Implementação simplificada para aprendizado, não código compatível com produção

O módulo do Intel 8051 do PubLab é um **modelo de ensino de uma arquitetura
histórica**, não um emulador e não uma ferramenta de desenvolvimento para
hardware 8051 real.

- Um programa que roda aqui **não** tem garantia de se comportar igual em um
  8051 físico, e nunca deve ser usado como referência para firmware,
  certificação, análise de temporização ou qualquer decisão de produção.
- Apenas um subconjunto explicitamente documentado do conjunto de instruções
  será modelado — o subconjunto de que os experimentos do laboratório
  precisam. O que está fora dele está **ausente, não aproximado**.
- Periféricos (portas, timers, UART) serão marcados como `conceitual` ou
  `baseado em <peça específica>`. O PubLab não inventa endereços,
  registradores ou comportamentos e os apresenta como hardware real.
- Contagem de ciclos, temporização e comportamento elétrico **não** são
  modelados.

## Situação: etapas A e B concluídas

Esta página é o escopo completo, marcado item por item como arquitetura
real ou abstração educacional (Regra 7 da especificação), aprovado antes de
qualquer código ter sido escrito. A implementação segue em etapas, cada uma
com seus próprios testes, do mesmo jeito que o Advanced Mode (fase 8) foi
construído nas etapas A-C.

- **Etapa A — concluída.** Núcleo: registradores, bancos de registradores,
  PSW, Internal Data Memory, Code Memory, instruções de
  `MOV`/aritmética/lógica, saltos, `CALL`/`RET`. Vive em `publab/i8051/`,
  sua própria toolchain autocontida (lexer, parser, assembler, engine) —
  não é um modo da PubVM, do mesmo jeito que isto é sua própria arquitetura,
  não uma variante de uma. Coberta por `tests/i8051_core_test.kf`,
  `tests/i8051_asm_test.kf`, `tests/i8051_engine_test.kf` e
  `tests/i8051_golden_test.kf`. Ainda sem aba na UI — a etapa A é a máquina
  e seu assembler, a mesma ordem que a PubVM seguiu (fases 1-2 antes da UI
  chegar na fase 5B).
- **Etapa B — concluída.** A porta `P0` de I/O, um registrador de verdade,
  legível e gravável (ver "Periféricos" abaixo).
- Timers (`T0`/`T1`), a UART e as outras portas (`P1`-`P3`) **não estão
  planejados para a fase 9** — ver "Explicitamente fora de escopo" abaixo.

## Registradores

| nome | largura | real ou abstração |
|---|---|---|
| `A` (acumulador) | 8 bits | real — endereço SFR `0xE0` |
| `B` | 8 bits | endereço real (SFR `0xF0`), mas **reaproveitado**: o hardware real usa o `B` como segundo operando/registrador de resultado alto do `MUL`/`DIV`, que este modelo não implementa (ver "Explicitamente fora de escopo"). Aqui o `B` é modelado como um segundo registrador geral, sem comportamento especial de instrução. |
| `R0`-`R7` | 8 bits cada | real — não é um register file plano: são **os primeiros 8 bytes do banco de Internal Data Memory que `PSW.RS1:RS0` seleciona no momento** (ver "Memória" abaixo). Ler `R3` depois de trocar de banco lê um byte diferente da memória real — esse aliasing é o próprio ponto de ensino desta arquitetura, e o modelo precisa preservá-lo exatamente, não fingi-lo com um register file separado. |
| `PC` | 16 bits | real |
| `SP` | 8 bits | real — **e cresce para cima**, o oposto da pilha da PubVM. O `PUSH` incrementa o `SP` primeiro, depois escreve no novo `SP`; o `POP` lê no `SP`, depois decrementa. O silício real reinicia o `SP` em `0x07`; este modelo faz o mesmo. |
| `DPTR` (`DPH`:`DPL`) | 16 bits | real, mas **restrito**: o hardware real usa o `DPTR` para `MOVX` (memória de dados externa, que este modelo não tem) e `MOVC` (ler a Code Memory como dado, para tabelas de consulta). Só o estilo de leitura do `MOVC` é modelado; o `MOVX` está ausente, não aproximado, porque não há memória externa pra apontar. |

`A` e `B` *não* são alcançáveis como endereço SFR mapeado na memória na
etapa A (o hardware real permite `MOV 0xE0, #5` como alias de endereço de
byte para `MOV A, #5`) — só a forma mnemônica do registrador nomeado está
implementada. Acesso a SFR mapeado em memória é uma possível etapa futura,
não a etapa A.

## PSW (Program Status Word) e flags

| bit | nome | real ou abstração |
|---|---|---|
| 7 | `C` (carry) | real |
| 6 | `AC` (auxiliary carry) | real — half-carry saindo do bit 3, definido por `ADD`/`ADDC`/`SUBB`, do mesmo jeito que o hardware real calcula (relevante para aritmética BCD, que este modelo não implementa de outra forma — o `AC` ainda é calculado corretamente mesmo que nenhuma instrução BCD o use ainda) |
| 5 | `F0` | bit real, flag de uso geral do usuário — modelado como um bit comum, legível/gravável; nenhuma instrução da etapa A o define automaticamente |
| 4-3 | `RS1:RS0` | real — seleciona o banco de registradores ativo (0-3) para `R0`-`R7` |
| 2 | `OV` (overflow) | real — overflow com sinal, calculado do mesmo jeito que a flag `O` da PubVM (mesmo raciocínio de sinal de operando/resultado), mas só no `ADD`/`ADDC`/`SUBB` |
| 1 | (reservado) | o hardware real deixa esse bit livre para o usuário definir; este modelo sempre o lê como `0` e ignora escritas nele, o que é uma simplificação documentada (peças reais variam aqui) |
| 0 | `P` (parity) | real — **recalculado depois de toda escrita no `A`**, não só depois de aritmética: sempre reflete a paridade atual dos bits do acumulador, exatamente como o hardware real |

Diferente da PubVM, o PSW do 8051 **não tem uma flag Zero persistente**. O
`JZ`/`JNZ` testa o valor atual do `A` no momento em que o salto executa, não
uma flag que uma instrução anterior deixou. Essa é uma diferença real e
conhecida entre as duas arquiteturas, e é uma das comparações para as quais
a fase 11 (comparação entre arquiteturas) existe.

Exatamente quais instruções mexem em quais flags — tudo real:

| instrução | C | AC | OV | P |
|---|---|---|---|---|
| `ADD`, `ADDC` | define | define | define | recalculado (A mudou) |
| `SUBB` | define (borrow) | define (borrow) | define | recalculado (A mudou) |
| `ANL`, `ORL`, `XRL` | não mexe | não mexe | não mexe | recalculado só quando `A` é o destino |
| `INC`, `DEC` | não mexe | não mexe | não mexe | recalculado só quando o operando é `A` |
| `MOV`, `JZ`, `JNZ`, `JC`, `JNC`, `JMP`, `CALL`, `RET`, `PUSH`, `POP` | não mexe | não mexe | não mexe | recalculado só quando `A` é escrito |
| `HALT`, `PRINT` (educacionais, não são 8051 real) | não mexe | não mexe | não mexe | não mexe |

Essa é uma diferença real e importante em relação à PubVM: `ANL`/`ORL`/
`XRL` **não** zeram `C`/`OV` do jeito que `AND`/`OR`/`XOR` da PubVM zeram o
`C`/`O` da PubVM — as instruções lógicas reais do 8051 simplesmente não
tocam nelas.

## Memória

```
Code Memory            4 KB     (peças reais vão de 4 a 64 KB; este
                                 modelo usa 4 KB — simplificação,
                                 documentada aqui — suficiente para
                                 todo exemplo que o laboratório traz)
Internal Data Memory   128 bytes, tamanho real do 8051 clássico
```

Layout da Internal Data Memory (tudo real):

```
0x00-0x1F   4 bancos de registradores (R0-R7), 8 bytes cada — selecionados por PSW.RS1:RS0
0x20-0x2F   memória endereçável por bit
0x30-0x7F   RAM de uso geral
```

**O acesso endereçável por bit (`SETB`/`CLR`/`MOV` num bit único) não está
implementado na etapa A.** A região `0x20-0x2F` existe e é memória real
neste modelo, alcançável com instruções comuns de byte — só as instruções
dedicadas de endereçamento por bit é que ficam para depois. Isso está
listado separado de "explicitamente fora de escopo" porque é arquitetura
real, só ainda não implementada, do mesmo jeito que as etapas da fase 8 da
PubVM deixavam mnemônicos posteriores explicitamente reconhecidos-mas-não-
implementados em vez de desconhecidos.

O espaço de SFR (`0x80-0xFF` no hardware real) **não** é modelado como uma
região de memória na etapa A: `PSW`, `SP`, `A`, `B` e (etapa B) `P0` só são
alcançados pelos mnemônicos de registrador nomeado, nunca por um endereço de
byte nessa faixa. Isso é uma simplificação em relação ao hardware real, onde
muitos SFRs realmente são mapeados em memória.

## Instruções — etapa A

Mnemônicos reais do 8051, um subconjunto deliberadamente pequeno:

| instrução | formas | notas |
|---|---|---|
| `MOV` | `MOV r, imm` · `MOV r, r` · `MOV r, direct` · `MOV direct, r` | `direct` é um endereço de Internal Data Memory, modo de endereçamento real |
| `ADD`, `ADDC` | `op A, r` · `op A, imm` | mnemônicos reais; o 8051 não tem um `SUB` registrador-a-registrador simples |
| `SUBB` | `SUBB A, r` · `SUBB A, imm` | real — "subtract with borrow"; não existe `SUB` sem borrow no hardware real também |
| `ANL`, `ORL`, `XRL` | `op A, r` · `op A, imm` | mnemônicos reais (não a grafia `AND`/`OR`/`XOR` da PubVM) |
| `INC`, `DEC` | `op r` | real |
| `JZ`, `JNZ` | `op addr` | real — testa o `A`, não uma flag (ver "PSW" acima) |
| `JC`, `JNC` | `op addr` | real — testa a flag `C` |
| `JMP` | `op addr` | **simplificação**: o hardware real oferece `AJMP`/`LJMP`/`SJMP`, três formas distinguidas pelo alcance do salto (uma questão de densidade de encoding do conjunto real, não um ponto de ensino para este laboratório). Um `JMP` só, alcançando toda a Code Memory, substitui os três. |
| `CALL`, `RET` | `op addr` / `op` | mesma simplificação do `JMP`: `ACALL`/`LCALL` reais colapsam num só `CALL` |
| `PUSH`, `POP` | `op r` | mnemônicos reais; o hardware real empilha/desempilha um *endereço direto*, não só um registrador nomeado — restrito aos registradores que este modelo nomeia, consistente com "`A`/`B` não são alcançáveis como endereço SFR" acima |
| `HALT` | `op` | **não é uma instrução real do 8051.** O hardware real não tem halt — um programa terminado é convencionalmente um auto-salto infinito (`HERE: SJMP HERE`). O PubLab acrescenta um `HALT` educacional, do mesmo jeito que o `PRINT` já é uma instrução educacional da PubVM e não da CPU real (seção 13 da especificação) — assim o laboratório tem um jeito honesto de terminar uma sessão passo a passo. |
| `PRINT` | `op r` | **não é uma instrução real do 8051**, reaproveitada ao pé da letra da PubVM pelo mesmo motivo do `HALT`: um jeito educacional de observar o valor de um registrador como saída, exatamente como o `PRINT` da PubVM (mesma justificativa, mesma redação, seção 13). |

## Explicitamente fora de escopo para a fase 9

Listado para que a fronteira fique registrada, não implícita pelo silêncio:

- **`MUL`, `DIV`** — as instruções que dão ao `B` seu propósito real.
  Ausentes, não aproximadas.
- **Instruções de endereçamento por bit** (`SETB`, `CLR`, `MOV`/`ANL`/`ORL`
  em nível de bit em `0x20-0x2F`) — a região de memória é real; as
  instruções que endereçam bits individuais ainda não estão implementadas.
- **`MOVX`** (memória de dados externa) — não há conceito de memória
  externa neste modelo.
- **Tabelas de consulta baseadas em `MOVC`, `XCH`, `SWAP`, `RL`/`RR`(C)`,
  instruções BCD (`DA`)** — instruções reais do 8051, simplesmente fora do
  subconjunto da etapa A.
- **Interrupções** (`INT0`/`INT1`, interrupções de timer, interrupção
  serial, `IE`, `IP`) — uma parte real e significativa do modelo de
  programação do 8051, totalmente fora de escopo para a fase 9. Se um dia
  for modelada, precisa de sua própria página de escopo sob essa mesma
  disciplina da Regra 7.
- **Timers `T0`/`T1`, a UART, portas `P1`-`P3`** — só o `P0` está planejado
  (etapa B). Os outros estão ausentes, não aproximados, até que uma fase
  futura os coloque em escopo explicitamente do mesmo jeito que esta página
  coloca o `P0`.
- **Contagem de ciclos, temporização, comportamento elétrico** (modelo
  elétrico de porta quase-bidirecional, frequência do oscilador) — nunca
  modelados, como dito no topo desta página.

## Periféricos — etapa B (concluída)

| nome | modelo |
|---|---|
| `P0` | **baseado no `P0` do 8051 clássico**: um registrador de 8 bits, endereçável por byte, diretamente legível e gravável. O `P0` real é eletricamente quase-bidirecional (um pull-up interno, saída open-drain, e lê o estado do pino, não o último valor escrito, quando configurado como entrada) — nada dessa nuance elétrica é modelado. O `P0` deste modelo se comporta como um registrador comum de leitura/escrita: o que foi escrito por último é o que se lê de volta. Essa lacuna é deliberada e está dita aqui, não deixada para o leitor descobrir. Usável em qualquer lugar onde um operando de registrador é aceito — `MOV P0, #0xFF`, `MOV A, P0`, até `ANL A, P0` — do mesmo jeito que uma porta real é um byte endereçável comum para qualquer instrução real do 8051, não um caso especial que só o `MOV` alcança. |

`P1`, `P2`, `P3` são nomes reservados, seguindo o mesmo padrão que o
Advanced Mode da PubVM usou para mnemônicos/registradores ainda não
implementados: reconhecidos pelo assembler e rejeitados com um diagnóstico
honesto de "não implementado nesta fase", nunca tratados como um
identificador desconhecido.
